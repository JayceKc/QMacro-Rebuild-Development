# Runner 如何接收缺失指令的配套資料

八組腳本的 3,261 筆缺失位置仍保留原樣。既有樣本保留記錄位置、標記和字串表，但這些位置的原 opcode 和 operand 已被清除。這次追到 Runner 接收這兩個值的路徑，並用保存的機器碼核對命令分派、腳本選擇及回覆分支。

## 專用合併訊息

1. 外層程式在 `0x40A118`、`0x40A121` 填入 `_MergeScriptKeyInfo_R` 的 `macro_id` 和 `key_info`。它在 `0x40A12B` 指定命令 `0x1F`，在 `0x42A217` 寫入封包標頭第 2 個位元組，序列化後於 `0x42A23F` 呼叫傳輸端。
2. Runner 在 `0x441AE6` 讀取標頭第 2 個位元組，於 `0x441AF0` 加上 `0x400`。`0x1F` 因此變成分派鍵 `0x41F`，對應 `0x440D38–0x440D62` 註冊的處理器 `0x444730`。
3. 處理器於 `0x444799` 解析訊息。解析器從還原的 Protobuf schema 得到兩個 bytes 欄位。欄位 1 `macro_id` 的物件槽位是 `+0x08`（`0x41E4F3`），欄位 2 `key_info` 是 `+0x0C`（`0x41E55C`）。
4. 處理器先用外層訊息的 `+0x0C` 選擇執行環境（`0x4447B0`），找不到便在 `0x444811` 走清理分支。進入 `0x4331C0` 後才以 `macro_id` 查找目標腳本（`0x42DEB0`）。查不到直接回傳 0。查到後以執行器 vtable 的 `+0x2C` 取得執行物件，並在 `0x433246` 呼叫 `0x60D9C0`，將 `key_info` 交給合併函式。
5. `0x4448EB` 回來後，處理器在 `0x4448F6` 將回覆參數 EDX 設為 0，再呼叫 `0x445730`。因此這條路徑上的零值回覆無法單獨證明找到目標或補回了指令。驗證合併要比較實際記錄位置與內容。

## 新增腳本時附帶的資料

`_AddMacro_R` 的欄位 1 `macro_run_data` 內，欄位 3 是 bytes 型別的 `merge_part`。Runner 於 `0x4309A2` 取出物件 `+0x10` 的字串，與 `0x813348` 的 `none` 比較。完全相等時跳至 `0x4309F5`，其餘會進入合併準備並呼叫同一個 `0x60D9C0`。大小寫有區別，空字串也會進入準備分支。

先前確認外層一般 AddMacro 送出路徑 `0x408750` 沒有填入 `merge_part`，初始值為空。因此單靠看到合併函式被呼叫，也無法判定它收到含原指令的資料。

## 傳輸內容和離線解碼

外層 `0x604950` 先序列化 Protobuf，再於 `0x604A14` 交給 `0x62CE10`。這個函式把資料長度補到下一個 8 位元組邊界，將填補長度寫入最後一個位元組，再加密。Runner 在需解密的接收分支依外層物件 `+0x0C` 的識別查詢連線資料（`0x441B58`），在 `0x441B7A` 解密、更新長度，再回到命令分派。處理器在 `0x44478D–0x444799` 以 `+0x14` 的緩衝區和 `+0x08` 的長度進入 Protobuf 解析。

用公開的 8 位元組測試金鑰和零 IV 核對兩個分組。外層 `0x42DC80` 加密輸出與獨立 DES-CBC 參考相同，Runner `0x453870` 解回原始位元組。這是傳輸層的加密，配套 ZIP 內部仍以原本的 ZIP 解碼規則驗證。測試沒有擷取實際連線金鑰或封包。

`recover_qmacro_key_info.py` 的 `--input-format merge-message` 或 `--input-format add-message` 接受**已解密並切出的 Protobuf payload**。原本直接讀配套檔的用法維持。檢視時只需指定輸入及新的 `--output-directory`。還原時另需指定 `--script-decoded`、`--expected-script-sha256` 及 `--expected-macro-id-hex`。AddMacro 使用 `macro_info.macro_id`（內部欄位 15）。工具逐位元組比對識別，並拒絕重複目標欄位、截斷資料、空配套及 CRC 錯誤。來源與腳本的歸屬仍需由同一次擷取或其他原始紀錄確認。

## 驗證及後續取證

- [機器碼錨點與重播結果](merge-message-route-verification.json) 包含 57 個反組譯錨點、17 組有界重播。分派到呼叫邊界即停止，沒有送出訊息。腳本查找、執行器選擇、字串包裝及合併使用受控替代，實際合併指令值仍未知。
- 若取得正確版本的原始配套資料，可從 `_MergeScriptKeyInfo_R.key_info` 或 `_AddMacro_R.macro_run_data.merge_part` 取出內容，並用已知腳本識別及來源配對。另一個可驗證來源是同版本未移除指令的原始 QMS。
- 現有 `work/recover_qmacro_key_info.py` 可離線核對配套 ZIP 的成員名稱、原始大小、CRC 及逐筆指令範圍。ZIP 完整性和腳本來源配對是分開的驗證。既有 20 份解封副本與本機候選掃描尚未找到真實配套內容。
